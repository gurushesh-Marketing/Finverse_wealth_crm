# Finverse CRM v2 — 31 October release gate

Status: **NOT READY**. This is a working release plan, not evidence that the CRM is production-safe. The user operates the Hostinger VPS and performs the deployment manually; development agents prepare and verify the release.

## Architecture decision

Keep the existing React/Vite web app, Express API, Zod contracts, custom session/auth flow, and PostgreSQL repository. Self-hosted Supabase **contains PostgreSQL**; it does not replace it. A Supabase deployment may supply the PostgreSQL service through a direct database connection while the application continues to use `pg` and its existing forward migrations. Do not switch to Supabase Auth, REST, Storage, Realtime, or a browser-side service key in this release. The current app uses a PostgreSQL advisory lock, so validate the direct/session connection path in staging before cutover.

If self-hosted Supabase is mandatory for the 31 October release, rehearse its Docker stack and a database copy on an isolated staging host before production. If the rehearsal cannot pass every gate below, postpone production cutover and show the verified local demo. Preserve the existing database until a verified backup and rollback path exist.

## Single issue ledger

Use one row per reproducible defect in `docs/process/RELEASE_ISSUES.md`: ID, user journey, environment/revision, observed failure, expected behavior, owner, first failing test, fix revision, retest result, status. A report or green isolated test does not close a row; close it only after the same browser journey passes against the intended environment. Do not restart identical failed work more than twice without a new hypothesis.

## Release sequence

1. **Freeze and preserve:** inspect the dirty working tree, separate intended source/migrations from generated screenshots and diagnostic scripts, run `git diff --check`, and create a reviewed Git checkpoint. Do not discard existing work or operational data.
2. **P0 journeys:** reconcile Super Admin identity and onboarding (including pending EMP-035), HR request -> SA decision -> account activation -> first login, four-vertical roster/team permissions, Data Entry bulk publish -> fair same-team round robin -> caller inbox/priority. Record real browser and API evidence. The employee ID is immutable; SA chooses a unique permanent login username linked to it. The historical statement that the username must equal the employee ID is superseded.
3. **Deployment path:** prepare a Hostinger VPS staging environment using a pinned self-hosted Supabase release, unique secrets, TLS/reverse proxy, firewall, persistent volumes, and a direct database URL available only to the API. Verify host resources against the official Supabase minimum and recommended requirements. The user performs VPS actions; agents provide exact reviewable commands and checks.
4. **Data rehearsal:** back up the operational PostgreSQL source, restore into isolated staging, check server-major compatibility, apply forward migrations only as needed, compare schema versions and row counts, and verify application login plus role/vertical/team isolation. Perform and time a restore drill. Never run a reset or seed against production data.
5. **Release verification:** typecheck, lint, build, focused API tests, browser journeys on desktop/mobile, independent access/security review, API liveness and **database-backed** readiness, and smoke tests through the real reverse-proxy URL. Verify logs, rate limiting, cookie flags, backup schedule and restore instructions. Disable demo credentials and synthetic-data conveniences in production.
6. **Go/no-go:** release coordinator lists every P0 row and evidence. The user decides whether to deploy. If any P0 journey, backup/restore, TLS, or access isolation gate fails, label the build demo-only and keep production unchanged.
