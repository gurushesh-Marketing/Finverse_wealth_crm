## 4. Shared System Foundations (Deck Pages 314–318)

The action deck defines five core pages of non-negotiable cross-screen logic that bind every vertical, workspace, and transaction:

### Shared Logic 01: Identity, Session, and Role Scope (Page 314)
- **One role interface per active workspace:** Authentication resolves the active approved role. The navigation shell renders only modules permitted to that specific role. No cross-role switcher, other-role menu, or impersonation mode exists.
- **Scope filters are not role switches:** A Team Lead managing multiple granted teams uses team filters inside the single TL interface. Cross-vertical grants operate via scoped filters, never dashboard impersonation.

### Shared Logic 02: Historical Attribution & Control Outcomes (Page 315)
- **History does not reopen old access:** Employee identity, historical assignment intervals, ownership periods, and metric facts are immutable. Transfers or promotions update current permissions only; prior personal scorecards remain read-only in Career History with customer PII restricted.
- **Every visible control has a defined outcome:** `Apply filters` slices the current view; `Reset` restores defaults. `Cancel` or `Close` aborts without committing. `Save draft` stores local progress without triggering system commits or approval transitions. `Submit` triggers atomic validation and locks the submitted payload.

### Shared Logic 03: Lead Lifecycle & Approval Hierarchy (Page 316)
- **Core lead state machine:** `Not contacted` → `Contacted` → `Follow-up` → `Pending conversion` → `Converted`. Direct progression from `Contacted` to `Pending conversion` is permitted only when product evidence is fully verified. Open leads may become `Lost` only with an approved reason code. `Reopen` requires formal approval.
- **Approval and delegation rules:** The default reviewer for sales conversion requests is the scoped Team Lead. TL self-submissions route automatically to the Manager queue (`requester != decider`). Workload rebalances crossing granted team boundaries route to Manager approval.

### Shared Logic 04: Scheduled Cadences & Multi-Vertical Isolation (Page 317)
- **Standardized calendar:** Asia/Kolkata (+05:30 IST), Monday-starting weeks, April–March fiscal year. Scheduled jobs produce immutable completed-period snapshots at 00:15 local time with safe retry and deduplication.
- **Four configurable verticals:** Wealth Management, Commercial Banking, Markets / Securities, and Real Estate Advisory share the core identity and scheduling engines while maintaining strict data and entity isolation.

### Shared Logic 05: Acceptance Scenarios & Failure Guards (Page 318)
- **Mandatory acceptance tests:** Wrong-role URL access, out-of-scope prospect access, cross-vertical search, revoked team grants, promotion during active session, employee exit with pending tasks, duplicate webhook replay, and midnight/quarter boundary calculations must be verified with automated server-side denial and clean UI error states.

## 7. Measurable Completion Gates (Definition of Done)

An action or feature is considered **DONE** only when all five criteria are fulfilled:
1. **Implementation Evidence:** Source code committed in `apps/web`, `apps/api`, `packages/contracts`, or `database/migrations` satisfying all deck fields.
2. **Executed Positive/Negative Tests:** Automated tests executed with recorded PASS evidence (Node test runner for API journey suites, Playwright e2e for browser flows).
3. **Permission Checks:** Server-side SQL authorization verified (role, vertical, team grant, effective dates). Hidden UI elements do not count as security.
4. **Persistence Evidence:** Real PostgreSQL transactional commits (`BEGIN ... FOR UPDATE ... COMMIT`), audit event logging, and immutable timestamps.
5. **Rendered-Screen Acceptance:** UI verified in a real browser against the action deck mockup and brand guidelines (typography loaded via `document.fonts`, computed colors matching hex tokens, single solid primary button).

### Status Definitions
- **Verified:** Complete end-to-end implementation with executed test evidence and verified brand styling.
- **Simulated:** Feature behaves according to contract but connects to a mock or simulated adapter (e.g. simulated telephony provider, mock WhatsApp API, quarantine scan). Simulated features **cannot be claimed as production-ready**.
- **Partial:** Component or endpoint implemented but missing deck fields, drawers, or mobile responsiveness.
- **Blocked:** Implementation cannot proceed due to unresolved review findings (e.g. TL findings M1–M5) or missing prerequisites.
